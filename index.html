Approach

Strategy sets the question. One loop delivers the answer.

Analytics only matters if it changes what the business does next. Every piece of work starts from the strategy, meaning the bets leadership is making and the decision in front of them, runs through the same four-step loop whether it is a one-week analysis or a year-long data layer, and ends in a review that records what changed and feeds the next plan.

01

Strategy: start from what the business is trying to win

Which bets leadership is making, which metrics they plan against, what a good quarter looks like. The measurement strategy is written against that, with the documented-versus-estimated line drawn and definitions agreed with the people judged by them before anything ships.

02

Delivery: define, discover, deliver, iterate

The same spine for every piece of work. The comparison bar and the acceptance criteria are locked in Define, so the readout cannot be argued with later; the data layer is built in Deliver with declared grain, tests and one semantic layer that people, dashboards and AI agents read the same way.

03

Iterate: change the decision, record it, feed the next plan

Weekly reviews run off the facts, not decks. Readouts lead with the answer, the review notes what changed because of the number, and the open question goes back into the next planning cycle.

AI-native GTM · data for agents

A GTM engine's data layer, built for an LLM to read

Production models behind an AI account-intelligence tool for account executives: defined grain, tests, review, incremental with a lookback. The brief was a 50% token cut; text cleanup alone delivered under 10%, so I reframed the problem at the data layer, where 722K raw activity rows become 33K thread-evidence rows before the model sees them. Day to day the same pattern runs my own work: Cursor and Claude in the workflow, a knowledge base over my own documentation, reusable agent skills for repeat analyses.

What it changedAn AI account tool reps actually use, and a pattern the team now follows: reduce before you prompt, and treat token cost as a data-modeling question.
log scale · one row per thread · 95% reduction

Values

The way I work, written down.

Communication

Lead with the answer, put it in writing

Executive readouts open with the decision and the number behind it. Bad news goes out early, written down, with the next step attached. If a stakeholder is surprised in the review, the communication already failed.

Collaboration

One team across Marketing, Sales, Finance and RevOps

Definitions are agreed with the people who will be measured by them before anything ships. Credit is shared, the partner's goal is the goal, and nobody relitigates the number in the review.

Ownership

If the number is wrong, it's mine to fix

I own the work from the question to the decision, whoever built the model. "Corrected" is not "generated," and a result that is bad news ships with the same confidence as good news.

Empathy

Start from what someone has to decide

Every piece of work begins with the decision it serves and the person making it. Tools get built for the rep who has to use them, not for the demo. If a number won't change what happens next, it doesn't get built.

Impact over activity

Fewer metrics, fewer rows, fewer tools

Most trust problems are complexity problems. I would rather retire three dashboards than add a fourth, and the review notes what changed because of the number, not how many reports shipped.

Learn, grow, teach

Leverage is other people doing it well

Curricula, office hours, mentoring analysts without a reporting line, standards written down so the function works when I'm not in the room. I pick up new tools quickly and hand them on; the team's ceiling, not my output, is the measure.
